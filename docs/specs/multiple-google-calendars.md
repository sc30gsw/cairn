# 複数 Google カレンダー連携

- 状態: 実装済み。2026-09-07。ユーザーの実装指示により、設定変更・解除を含む本計画を採用。実 Google アカウントとの OAuth・書き込み検証は別途テスト用アカウントが必要。
- ブランチ: `codex/multiple-google-calendars`
- 依頼: 実行ボードに複数 Google Calendar を接続する機能を追加する。先に `grill-with-docs` で計画を作る。
- 既存仕様: [calendar-sync.md](./calendar-sync.md)
- 関連する決定: [ADR-0016](../adr/0016-google-login-replaces-notion.md)、[ADR-0017](../adr/0017-google-calendar-two-way-sync.md)、[ADR-0018](../adr/0018-multiple-google-calendar-connections.md)、[ADR-0019](../adr/0019-calendar-connections-do-not-grant-sign-in.md)

## 確定した目的と範囲

Q1: 所有者が持つ2つ以上の Google アカウントを同時に接続し、既存の実行ボードの予定タブで複数アカウントの予定を確認する。

個人用と仕事用のアカウントを持つ所有者は、今は片方の予定しか見られず、正確な空き時間を判断できない。両方の予定を同じボードで確認して、学習の予定を置けるようにする。2アカウント限定という意味ではない。独自の2件・5件という固定上限は設けず、ページ単位の処理で対応する。

利用例は、個人用の予定が18時〜19時、仕事用の会議が19時〜20時にある日に、両方をボードで確認できること。

参照はユーザー指定の [Spir 紹介ページ](https://www.spirinc.com/lp005)。公式ヘルプにも、メイン以外のカレンダーを重ねて確認する説明がある。[複数のカレンダーと連携する](https://help.spirinc.com/ja/複数のカレンダーと連携する)

用語集では、Google アカウント1つとの連携を「カレンダー接続」とする。1つの所有者が複数の接続を持つ。`CONTEXT.md` は今回合意した語義を反映し、現行の同期・解除規則は [calendar-sync.md](./calendar-sync.md) にまとめる。

Q2: Cairn の予定・本番日・未達成チェックポイントの期限の書き込み先は、所有者自身が設定で選ぶ共通の Google カレンダー1つ。個人用アカウントへの固定や、接続先のメインカレンダーへの固定はしない。会話中の「個人用」は利用例であり、アプリが自動で選ぶ条件ではない。予定ごとに書き込み先を変えたり、すべての接続に複製したりする運用は採用しない。後から書き込み先を変更する場合の既存予定の扱いは Q6 で決める。

Q3: 追加する仕事用などのカレンダー接続は、外部予定を確認するための閲覧専用接続とする。会議には他の参加者がいるため、Cairn から一方的に変更しない。Google 側で編集権限があっても、Cairn のドラッグ・件名や時間や色の編集・削除を認めず、バックエンドからの外部予定の更新要求も拒否する。現在の接続の外部予定の編集機能は維持する。

Q2 の書き込み先は、Cairn が書き込みを許可されたカレンダーから選ぶ。閲覧専用接続を暗黙に書き込み可能へ変えない。別アカウントへの書き込み先変更で権限の追加が必要な場合の操作は、保存先を選ぶ操作から追加の同意画面へ進む。

書き込み先に選ぶことと、その接続にある外部予定を編集可能にすることは別の判断。書き込み先の切替によって、仕事用の会議を変更しないという Q3 の制限を外さない。

Q4: 既存ボードに複数アカウントの予定を重ねて表示し、所有者が空白から空き時間を判断する形で十分。今回、空き時間の自動判定や強調表示は追加しない。空き時間の自動判定にだけ必要な勤務時間・最短時間・候補抽出などの設計分岐は閉じる。

Q5: 追加 Google アカウントはカレンダー連携専用とし、Cairn への新しいログイン手段にはしない。所有者はすでに個人用 Google アカウントで Cairn にログインでき、仕事用の Google アカウントをログインに使う必要はない。既存の個人用 Google ログインは維持し、カレンダー接続の追加・再認可・解除によってログイン権限を追加したり剥奪したりしない。ログイン画面からボタンを隠すだけでは要件を満たさず、認証処理でも区別する。

Q7: Google 側の変更を、ボードの予定タブを開いたとき、手動の「今すぐ同期」、毎日日本時間の2時・14時に取り込む。毎時同期を1日2回へ変更する。ボード表示中の5分ごとの取得や、フォーカス復帰時の追加取得は導入しない。

Q7 は Google からの定期取得の頻度を決めたもの。Cairn で予定を変更した直後の Google への送信、初回接続の取り込み、表示対象を追加した直後の取り込み、失敗した送信の再試行は別に維持する。開いたままのボードでは次の取り込みまで変更が見えないことがあるため、既存の「今すぐ同期」と最終同期時刻を使えるようにする。

Q8: 同じカレンダーの同じ Google 予定を複数の接続から取得しても、ボードでは1件だけ表示する。実際のカレンダー ID と予定 ID で判定し、別カレンダーに届いた同じ会議の招待や、件名・日時が偶然一致する別の予定はまとめない。

Q9: 仕事用の外部予定も、Google で閲覧権限がある会議名・日時をボードに表示する。詳細画面では取得元のアカウントとカレンダー名を確認できる。件名を見せることと、外部予定を編集できることは別であり、仕事用予定の閲覧専用という Q3 の制限は変えない。

## 合意した設定・解除の挙動

以下は、計画全体への実装指示により採用した挙動。

| 場面 | 採用する挙動 |
| --- | --- |
| 書き込み先を後から変更する | 同期対象に残る Cairn 発の既存予定・本番日・期限も、選び直したカレンダーへ移す。旧書き込み先に複製を残さない。Google で直接作成した外部予定は対象外 |
| 書き込み先を持たない接続を解除する | その接続の取り込みと Cairn が持つ写しを削除する。他の接続と Google 上の外部予定は維持する。同じ共有予定を別接続で表示している場合は表示を続ける |
| 書き込み先を持つ接続を解除する | 既存仕様に合わせ、Cairn がその出力先へ作った Google 予定を削除することを画面で確認してから解除する。Cairn の学習予定・記録・目標は残し、書き込み先は未設定に戻す。削除できないときは解除を完了扱いにしない。Google 側で認可が失われている場合は、Google に予定が残る可能性を伝えてローカルの接続を解除できる形にする |
| 1つの接続だけ失効・失敗する | 他の接続は同期を続ける。失敗した接続の写しは最終取得時点のものとして残し、ボードに未同期のアカウントがあることと再接続の導線を表示する |
| 新しい接続の表示対象 | 現行と同じく、Google 側で表示中かつ予定の内容を取得できるカレンダーを初期選択し、アカウントごとに変更できる |
| 初回導入 | 既存の接続、表示選択、書き込み先、Google の予定 ID、ログイン権限を維持して移行する |

Q6 の例は、来週の「英語学習 19〜20時」を個人用のメインカレンダーへ書き出した後、設定で「学習専用カレンダー」を選び直すケース。この学習予定も新しい書き込み先へ移し、仕事用の会議を移すものではない。

独自の2件限定・5件限定という接続数上限は追加しない。取得・移行・同期はページ単位で処理し、件数の増加で1回の処理が無制限に大きくならないようにする。外部予定の取得期間は現行の過去30日〜未来90日を維持する。

## 設定画面とボード

ボードの既存「Google カレンダー連携」と、マイページのアカウント設定で共通の画面を使う。

1. 「Google アカウントを追加」からアカウントを選び、カレンダーの読み取りを許可する。
2. 接続ごとにメールアドレス、表示するカレンダー、最終同期、同期状態、再接続、解除を表示する。
3. 共通の「Cairn の予定の保存先」で、アカウントとカレンダーを1つ選ぶ。書き込み権限が必要な場合は、そのアカウントに対して追加認可を行う。
4. Google から戻っても、ボードの表示日・週・ビューと、開いていた設定を保持する。新規追加と再接続で、別のアカウントを誤って選ばない。
5. ボードは既存の予定色と日・週・月・年表示を使う。追加した仕事用の外部予定は詳細を開けるが、ドラッグ・件名・時間・色の編集と削除はできない。

表示対象のチェックを外す操作と、アカウントの解除、書き込み先の選択を区別する。表示から外しても書き込み先を変更せず、アプリ発予定の Google 側の変更を戻すために必要な取り込みは続ける。

## 実装順序

認証の分離を独立した2案で実装・検証して比較し、採用案を同期処理と画面に統合する。

1. 認証の分離を小さく検証する。導入済み Better Auth の拡張点で、既存の個人用ログインと token refresh を維持しながら、追加アカウントのログインを拒否できることを確認する。認証方式を置き換える前提にはしない。
2. 接続を所有者と Google アカウントで識別する形へ拡張する。トークンの対象、同期状態、同期カーソル、再試行、解除がどの接続のものか明確にする。1接続の失効や解除が別接続を壊さないようにする。
3. 共通の書き込み先を接続とカレンダーの組で保持する。アプリ発予定の対応表が実際の書き込み先を示し、外部予定の閲覧専用という制限とは別に扱う。書き込み先変更は、上記の既存予定の移行規則に従う。
4. 取得と操作を複数接続へ拡張する。外部予定をまとめてボードの範囲に返し、同じカレンダーの同じ予定を複数接続から取得しても1件に統合する。重複した予定を別の接続経由で編集することで、仕事用予定の保護を迂回できないようにする。
5. ボードとマイページの共通設定に、アカウント追加、アカウントごとの表示対象・状態・再接続・解除、ユーザーが選ぶ書き込み先を配置する。ボードの日付・ビューと OAuth の戻り先を保持する。定期取得は日本時間の2時・14時に変更し、仕事用予定も閲覧できる件名・日時を表示する。
6. 既存接続・対応表・外部予定を新しい識別単位へ移行する計画を作る。現在のログイン権限と編集可能な接続の扱いを保持し、移行だけで Google 上の予定を複製しない。
7. 受け入れ条件を既存の Convex・UI テストへ追加し、`vp check`・`vp test`・必要なビルドと画面操作で確認する。

## 接続・重複・競合の設計

- `calendarConnections` を `ownerId + googleAccountId` で識別し、公開 API は指定された接続が認証済み所有者のものであることを検証する。
- 同期カーソル、外部予定の写し、同期排他、状態、再試行、未送信変更を接続に紐づける。1つの接続の失敗を他の接続へ波及させない。
- 書き込み先は所有者の設定として `connectionId + calendarId` の組で保持する。外部予定の編集可否と、Cairn 発予定の出力許可と、ログイン許可をそれぞれ区別する。
- 写しは取得元の接続を保持し、ボードへの返却時は `ownerId + calendarId + googleEventId` で統合する。`primary` の別名ではなく実際のカレンダー ID を使う。`iCalUID` や件名・日時だけで統合しない。
- Google の変更日時を比較し、古い写しが新しい変更を上書きしないようにする。同時刻なら安定した取得元を選び、詳細の取得元表示も一致させる。Google から明示的な削除が返った場合は、別接続の古い写しから復活させない。権限喪失・非表示化・取得期間からの除外は、予定自体の削除と区別する。
- 外部予定を編集できる接続は所有者につき1つ。移行前の接続（無ければ最初に接続した Google アカウント）を `calendarOutputSettings.editableGoogleAccountId` に記録し、解除して同じアカウントを再接続しても編集できる接続として扱う。それ以外の接続は Q3 の閲覧専用。
- 定期取得は needsReauth・解除中の接続を対象にしない。再接続の完了時に初回同期を行う。
- 閲覧専用の取得元を持つ外部予定の編集保護は、表示中の写しだけから導出しない。別接続の raw ID を直接渡す、表示チェックを外す、旧再試行が残る場合も、サーバー側で再判定する。
- Cairn 発の予定が別接続から取り込まれても、外部予定として二重表示しない。アプリ側の予定・目標へ変更を戻す処理は、現在の出力先接続を基準にする。
- 接続ごとの同期排他に加え、出力先変更には所有者ごとの設定世代を使う。旧出力先へ積まれた送信・再試行・解除が新しい出力先を変更しないよう、実行前と結果保存時に接続・世代を検証する。
- 出力先切替は件数が多くても再開できるようにし、Google 側の部分的な成功を記録する。全件移動前に設定値を変えるだけで完了扱いにしない。移動中も既存アカウントを再認可でき、認可を戻してから「移動を再開」で続行する。再認可だけで保存先を変更しない。

### 定期取得の設定

既存の毎時同期を、UTC の5時・17時、すなわち日本時間の14時・翌2時に変更する。Convex の cron は UTC なので、予定する式は `0 5,17 * * *`。ブラウザ側のタイマーを使わず、既存の Convex cron の実行先を複数接続に対応させる。[Convex の cron 仕様](https://docs.convex.dev/scheduling/cron-jobs)

これは2時・14時に同期を開始する計画であり、その瞬間に全件反映を完了する保証ではない。ボードを開いていなくても定期取得を実行する。差分トークン失効時の再取得と既存の送信再試行を維持する。

### 既存データの移行

1. 新しい接続参照と出力先設定を追加できるスキーマにする。この段階で既存行にない必須フィールドを要求しない。
2. 既存の外部予定・カーソル・対応表・未送信変更・同期状態を元の接続に紐づけ、元のメインカレンダーを既定の書き込み先として保持する。Google の eventId、表示選択、Cairn の予定・記録・目標を変更しない。
3. 既存の Better Auth account を確認して、すでにあるログイン権限を維持する。新しく追加するカレンダー専用アカウントとは分ける。
4. owner だけを持つ旧 scheduled action を安全に処理する。複数接続の「先頭」へ振り分けず、元の接続を特定できる移行情報を使う。新しい処理へ切り替わった後に旧処理を継続させない。
5. バックフィル完了と旧処理の扱いを確認した後に、接続参照を必須化し、単一接続向けインデックス・互換処理を整理する。

接続解除の清掃を owner 全件清掃のまま流用しない。スキーマ移行と、Q6 のユーザー操作による Google 上の予定移動は別の処理として検証する。

## 計画時点の技術調査

- 認証アカウント、カレンダー同期の接続、Google カレンダーの識別子を区別する。アカウント一覧の先頭を同期対象とする現在の選択方法を、複数接続にそのまま使わない。
- Google Calendar API のカレンダー一覧と予定の読み書きでは必要なスコープが異なる。現行の `calendar.events` と `calendar.calendarlist.readonly` が設計に合うか確認する。[Google Calendar のスコープ](https://developers.google.com/workspace/calendar/api/auth)
- Q3 に合わせ、閲覧専用接続では読み取り用スコープを求める設計を検証する。過去に書き込み権限を与えた Google アカウントや複数接続から参照できる同じカレンダーでも、Cairn の閲覧専用という制限はバックエンドで守る。OAuth の権限だけに依存しない。
- カレンダー一覧はページングされ、読み取り・書き込みなどのアクセス権を返す。選択可能な対象と編集可否は、接続したアカウントの権限に従う。[CalendarList.list](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list)
- 差分同期の状態はカレンダーの取得条件とともに管理する。接続の追加・解除で別の取得元の状態を消さない設計が必要になる。[差分同期](https://developers.google.com/workspace/calendar/api/guides/sync)
- 導入済み Better Auth 1.6.28 は、同一 owner に複数の Google アカウントを保持できる。`providerId + accountId` で識別し、`getAccessToken` に渡す `accountId` は Google の subject。DB レコードの `id` とは異なる。根拠は導入済み `node_modules/better-auth/dist/api/routes/callback.mjs:97` と `account.mjs:298`。調査で返された `next` ブランチの API を混ぜない。
- 現行の `linkSocial` をそのまま使うと、追加 Google アカウントも同じ Cairn アカウントへのログイン手段になり、Q5 を満たさない。既存の `AUTH_DISABLE_SIGNUP` は新規作成の制限であり、リンク済みアカウントのログインを止めない。根拠は `convex/auth.ts:47`、`convex/lib/owner.ts:10`、導入済み Better Auth の `dist/oauth2/link-account.mjs:134`。
- OAuth 復帰時、Cairn は sessionStorage の印を見て引数なし `connect({})` を呼び、権限を持つ先頭の Google アカウントを選ぶ。今回接続したアカウントを特定する処理が必要。1.6.28 には OAuth state に保持する `additionalData` と account create/update hook があるため、所有者に紐づく一回限りの接続要求と実際の Google subject を結び付ける案を検討する。`updatedAt` 順やアカウント一覧の差分だけでは再認可・別タブの並走を区別できない。hook と Convex の連携動作は未検証。

### カレンダー連携とログイン権限を分ける設計候補

Better Auth 1.6.28 にアカウント単位のログイン禁止の標準設定は確認できなかった。自前 OAuth を新設する前に、既存のトークン保存・更新を使ったまま Google provider の `getUserInfo` 拡張で実現できるか検証する。

- 通常の OAuth callback と直接 `idToken` によるログインは、アカウント照合と session 作成の前に `getUserInfo` を呼び、`null` を拒否する。Google subject に対するログイン方針をここで確認する候補がある。導入済み `node_modules/better-auth/dist/api/routes/callback.mjs:80`、`sign-in.mjs:154`。
- `linkSocial` 起点の許可された連携は、サーバーが設定した OAuth state の `link.userId` と所有者の接続要求を照合する。クライアントの任意データだけでログイン禁止を迂回させない。
- `getAccessToken` の token refresh は `getUserInfo` を経由しないため、既存の更新処理を維持できる見込み。導入済み `dist/api/routes/account.mjs:284`。
- `session.create.before` だけでは今回の Google accountId を特定できず、provider 名を分けるだけでは通常 Google ログイン時のメール照合・暗黙リンクを防げない。
- 計画時点ではこの組み合わせは未実行だった。実装では2案を独立に検証し、要求ごとの provider と session 作成前の再検証を用いる案を採用した。`accountInfo` と token refresh は標準 provider の挙動を維持する。接続解除後も、Better Auth に残るアカウントが意図せずログイン可能にならないよう、ログイン方針はカレンダー接続とは独立して保持する。

## 文書と検証

回答で用語が定まった時点で `CONTEXT.md` を更新する。認証との境界や書き込み先など、代替案と意味のあるトレードオフがあり変更コストも大きい判断は ADR に残す。未回答の提案は既存の確定済み仕様に混ぜない。

実装計画には、既存の `convex-test` と Vite+ を使った接続ごとの所有者検証、失効・解除の影響範囲、同期の再試行、OAuth 復帰、既存接続の移行の検証を含める。次のシナリオを検証する。完了時の検証は `vp check`、`vp test`、変更内容に応じたビルドと画面操作を予定する。

既存の `vp test` は frontend、Convex の Node、Convex の edge-runtime の3 project を含む。`AGENTS.md` の「src 配下だけ」は現行 `vite.config.ts:291` と一致しない。テストユーティリティは `vite-plus/test` から使い、別途 Vitest を追加しない。

Q2〜Q3 から必要になる検証は次のとおり。

- 個人用と仕事用の予定を同じボードで取得・表示できる。
- メイン以外のカレンダーを選ぶと、Cairn の予定は選んだ書き込み先だけへ送信される。
- Google 上で writer / owner の権限がある仕事用アカウントでも、閲覧専用接続の外部予定はドラッグ・編集・削除できない。
- 公開 mutation を直接呼んでも、閲覧専用接続の外部予定の変更は拒否される。外部予定の変更を送る内部処理も、その接続では外部予定の更新 API を呼ばない。
- 現在の接続の双方向同期と、編集可能な外部予定の操作が維持される。

Q4〜Q5 から必要になる検証は次のとおり。

- 個人用と仕事用の予定が日・週・月・年の既存表示に入り、アカウントを追加しても表示中の日付・ビューを保持する。
- 仕事用 Google アカウントのカレンダー接続は成功するが、そのアカウントでの通常 OAuth ログインと直接 `idToken` ログインからは Cairn の所有者の session を発行しない。
- 接続の取り消し・再認可・解除の途中や直後も、追加 Google アカウントがログイン手段に変わらない。
- 個人用 Google アカウントの既存ログインと、カレンダーの再認可・token refresh が引き続き動作する。

Q9 から必要になる検証は、仕事用の会議名・日時と取得元を確認できること、詳細を開いても編集・削除はできないこと、Google から件名を取得できない予定について権限外の情報を表示しないこと。

Q7〜Q8 と接続単位の処理から必要になる検証は次のとおり。

- 3アカウント以上の同時維持、新規追加・再認可・別タブ並走での対象特定、別所有者の接続 ID を使った操作の拒否。
- 定期取得が JST 2時・14時で動き、予定タブ表示時・手動でも取得する。5分タイマーを追加せず、Cairn での変更の即時送信を維持する。
- 同じ calendarId と eventId は1件、別 calendarId の同じ会議・同名同時刻の別予定は別件。古い写しから削除済み予定を復活させず、Cairn 発予定の反射も二重表示しない。
- 別接続の raw ID、非表示化、旧 retry でも仕事用外部予定の編集保護を迂回できない。
- 1接続の解除・失効・失敗が、他の接続の写し・設定・予定を消さない。出力先変更と旧送信・解除の競合でも二重送信や誤削除を起こさない。
- 既存データを段階的に移行し、Google の予定を複製しない。元の書き込み先とログイン権限を維持し、旧 scheduled action の扱いを確認する。
- 最終確認で合意した Q6 と接続解除の規則を満たす。実際の Google への接続や書き込みを伴う検証は、対象のテスト用カレンダーを明確にして行う。

実装完了時は `vp check`、`vp test`、`vp build` と該当する react-doctor の指摘を確認する。画面ではアカウント追加・書き込み先選択・OAuth 復帰・仕事用予定の操作不可・重複排除を確認する。
