# 記録・プリセット行の実行手順フィールドを「ひとこと」に改名し、任意にする。具体的手順は目標・障害プランに残す

記録とプリセット行が持つ実行手順フィールドの必須制約(1文字以上)を外し、名前も分離する。目標の内容・障害プランの then は「具体的手順」のまま必須(「〜を勉強する」を書かせない摩擦を維持)。記録・プリセット行の同じ位置のフィールドは「ひとこと」と改名し、空を許す。確定時のバリデーションゲート(`assertConcreteAction` / `ConcreteActionSchema`)を `rows.confirm` / `presets.create` / `presets.update` / `catalog.ensureCatalog` の4経路から外す。共有文はひとこと空の行を `項目名 N分` として出し、そのカテゴリの確定記録がちょうど1件かつ項目名がカテゴリ名と一致する場合に限り、見出しと1行に畳む。カテゴリが1つなら見出しを省略する旧規則は廃止し、畳み判定は「1件かつ項目名一致」の1条件だけに統一した。

具体的手順の必須は元々「抽象目標(『英語を勉強する』)を書かせない」ための意図的な摩擦であり、目標・障害プランのように実行前に書く欄では今も有効。しかし記録は実行後に確定するものであり、実際の運用では「英会話 30分」のように、項目名だけで用が足りて書くことがない日が定常的に発生する(模試の点数や教材の単元など、書く価値がある日だけ埋める)。同じフィールドに「実行前の最初の一歩」と「実行後の一行の補足」という2つの役割を負わせていたことが、共有文の手打ち補正(見出しの畳み・空行の有無)を招いていた。名前を分けることで、コードとグロッサリの両方が「なぜ記録だけ任意なのか」を説明抜きで表せる。

却下案は4つ。(1) ひとこと専用に実績フィールドを新設し、具体的手順とは別に持つ案 — 記録は1フィールドのままの方が共有文のロジックを1本に保てるため不採用。(2) `ConcreteActionSchema` 自体を緩めて目標・障害プランも任意にする案 — 実行前に書く欄の摩擦は今も有効なため不採用。(3) 項目ごとに「ひとこと不要」フラグを持たせる案 — 新概念とマイグレーションを増やす割に、任意化だけで足りるため不採用。(4) ひとこと空で確定するときに確認モーダルを出す案 — 自分で書く欄であり、空にした判断はその場で完結する。確認する相手がいないため不採用。
